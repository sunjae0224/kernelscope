# 5분 발표 시나리오

실행: 프로젝트 루트에서 `bash scripts/demo.sh` → <http://localhost:8501>.
GPU를 사용하지 않고 저장된 실험을 설명할 수 있다. 새 측정은 `bash scripts/campaign.sh`로 별도 실행한다.

후속 검증 화면: [모델·시드별 비교](img/dashboard_followup.png) · [정책 선택 비용](img/dashboard_followup_cpu.png). 최종 캠페인은 `followup_fullwarmup_20260922`, 짧은 워밍업 예비 캠페인은 `followup_20260922`다.

## 0:00–0:40 · 질문

“LLM 서버는 서로 길이가 다른 요청을 함께 처리합니다. 같은 attention을 계산하더라도 GPU에 일을 나누는 방식이 다르면 전체 생성 시간도 달라질까요?”

먼저 위쪽의 실측 데이터 규모와 캐시 조건을 보여준다. **커널 실측 / 모델 예측 / 전체 모델 실측**이 다른 종류의 근거라는 것을 설명한다.

## 0:40–1:40 · 병목과 입력 조건

**병목 진단**에서 cold, dense, 작은 배치의 긴 KV를 선택한다. 실행 블록 수가 작으면 GPU 전체에 충분한 일을 분배하지 못한다. split-KV는 긴 KV를 나누어 여러 블록이 처리한 뒤 결과를 합친다. 분할·합치기 비용이 있으므로 많이 나눌수록 항상 빠른 것은 아니다.

**커널 지도**에서 uniform과 mixed 길이 분포를 비교한다. 기존 S1 dense cold 실험의 uniform 중앙값 손실은 약 0.7%였다. 반면 긴 요청 2개(32K)와 짧은 요청 30개(1K)가 섞인 기록에서는 휴리스틱 3.54ms, 고정 split 0.52ms였다. 여기의 배수는 **attention 커널**에만 해당한다. dense와 paged의 수치를 섞어서 비교하지 않는다.

## 1:40–2:40 · 하드웨어 가설

**하드웨어 가정**에서 SM 수, 메모리 대역폭, 공유 메모리를 바꾼다. “SM 수를 늘리면 무조건 빨라질까?”를 묻고 충분한 병렬 작업이 있는지 확인한다. 공유 메모리 용량은 한 SM에 동시에 배치할 수 있는 블록 수를 바꿀 수 있다.

이 화면의 값은 보정된 대리 모델의 **예측**이다. 실측이 아니다. 예측 시간의 평균적인 오차가 작아도 항상 가장 빠른 커널을 고르는 것은 아니며, 검증 표의 실패 조건도 보여준다.

## 2:40–4:20 · 실제 생성 결과

**실제 생성**에서 Qwen3-4B 캠페인을 고른다. uniform, ragged, arrivals 실험을 차례로 비교한다.

2026-09-22의 `graduation_20260922/ragged`를 시연 사례로 사용한다. 요청은 **32K 1개 + 512토큰 31개**, 각 요청의 생성 길이는 64토큰이다. **실측표 선택의 TPOT는 61.06 → 33.80ms, 약 1.81배** 개선됐고 각 정책을 5회 반복한 생성 토큰이 모두 일치했다. Attention은 36.87 → 9.24ms/step, CPU 선택을 포함한 전체 decode는 51.36 → 24.08ms/step이었다. 토큰 간 지연에는 prompt admission 대기가 포함되어 decode 시간과 숫자가 다르다.

대조군도 반드시 보여준다. Uniform에서는 실측표 선택의 개선이 거의 없었고, 모델 선택은 초기 계산 비용 때문에 오히려 느렸다. Uniform의 고정 split 8은 생성 토큰 일치 검사를 통과하지 못했다. 따라서 “항상 split 8을 쓰면 된다”는 결론을 내리지 않는다.

1. **attention 시간**: 선택 변경이 직접 영향을 주는 부분.
2. **전체 decode 시간**: attention 외 projection, 정규화, MLP 등 모든 레이어 연산을 포함.
3. **정책 선택 비용**: 모델 계산이나 표 조회에 걸린 CPU 시간. 캐시 첫 실패와 이후 호출의 차이에 유의.
4. **TPOT와 반복 변동**: 요청이 실제로 토큰을 받는 간격. 새 요청의 prefill 때문에 생긴 정지 시간도 포함한다.
5. **토큰 일치**: 출력이 같은지를 성능과 함께 확인한다. 일치 검사가 실패한 결과는 출력 보존 성능 개선으로 제시하지 않는다.

좋아진 경우와 나빠진 경우를 함께 보여준다. 특히 복잡한 예측 모델이 첫 호출에서 많은 CPU 시간을 쓰면, 커널 선택이 좋아도 전체 생성은 느려질 수 있다. 가벼운 실측표가 더 나을 수 있다는 것 역시 결과다.

## 4:20–5:00 · 기여와 한계

“이 프로젝트는 커널 하나의 벤치마크에서 끝나지 않고, 입력 길이 분포에 따른 원인을 찾고, 실제 사전학습 모델의 생성 과정에 적용해 이득과 비용을 검증했습니다.”

후속 결과는 **실제 생성 → 일반화 검증**을 열어 보여준다. `heldout_text`를 고르면 두 모델·두 시드의 자연어 구성 실험을 볼 수 있다. 모델과 시드별 결과가 분리되어 있고, 출력 불일치는 속도 개선 배율에서 제외된다. 아래 정책 비용 그래프에서는 첫 호출과 이후 cache miss·hit를 구분한다. C 실행 경로는 같은 예측을 계산하는 첫 선택 비용을 줄였다.

단일 RTX 4090의 실험이며 운영 서버 전체나 여러 GPU로 일반화하지 않는다. 초기 실험은 합성 토큰, 후속 실험은 길이를 통제한 자연어 문단을 사용한다. 표준 언어 품질이나 HTTP 부하를 평가한 것은 아니다. 실제 요청 분포, 다른 GPU, 운영 서버 통합은 별도 검증이 필요하다.

## 질문에 답할 때

- **왜 그냥 기존 라이브러리를 쓰지 않나요?** 균일 조건에서는 기존 선택이 잘 작동했다. 개선 대상은 긴·짧은 요청이 섞인 조건이며 모든 입력에 개선을 주장하지 않는다.
- **새 attention 알고리즘인가요?** 기존 정확한 attention 구현의 실행 설정을 선택한다. 새로운 수식보다 측정·설명·선택·전체 모델 검증을 연결한 시스템 기여다.
- **몇 배 빨라졌나요?** 선택한 실험 화면의 지표와 반복 결과로 답한다. 커널 배수와 전체 생성 배수를 구분한다.
- **모델 예측이 틀리면요?** 검증 실패를 표시한다. 실측표와 고정 설정을 비교 기준으로 유지하고, 추천값은 실제 실행으로 확인한다.
- **결과를 다시 만들 수 있나요?** 시나리오 YAML, 정책 설정, 패키지 버전, 모델 경로, seed, 코드 상태와 실험 결과를 함께 저장한다. portable bundle의 원본 파일 해시도 제공한다.
