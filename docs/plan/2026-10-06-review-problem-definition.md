# 검토: 문제 정의, 관련 연구와의 관계, 작품의 미비점, 인계의 개연성 (2026-10-06)

작성 2026-10-06, 2026-10-02 캠페인([결과](../experiments/2026-10-02-hybrid-validation.md))까지의 기록을 바탕으로 한 검토. 최종 보고서 1·2장과 PLAN §0 수정의 근거로 쓴다. 외부 문헌의 서술은 아래 출처에서 확인한 범위로 한정한다.

## 1. 문제 정의는 맞게 서 있는가

현재 정의(PLAN §0): "길이가 다른 요청이 한 배치에 섞이면 FlashAttention의 KV 분할 수(num_splits) 휴리스틱이 GPU를 채우지 못한다. 이를 실측으로 진단하고, 시뮬레이터·성능 모델로 설명·예측하며, 매 decode step의 분할 수를 동적으로 골라 실제 LLM 생성에서 검증하는 시스템."

**현상 자체는 충분히 입증됐다.** 6,801조건 실측에서 균일 길이 손실 중앙값 0.72% 대 혼합 길이 최악 12.53배(연속 KV)·3.84배(페이지 KV), CTA 작업량 분석의 부하 불균형, 전체 모델 TPOT 1.81배(혼합 길이)·1.17배(요청 도착)·균일 1.00배, 그리고 `serve diagnose`로 "균일 배치에서는 attention 비중이 19.2%라 고를 여지가 없다"까지 — 원인과 효과의 사슬이 실측으로 닫혀 있다.

**정의에서 고칠 점 네 가지.**

1. **대상이 너무 넓게 적혀 있다.** 문제는 "FlashAttention"이 아니라 *FlashAttention-2의 decode 경로(`flash_attn_with_kvcache`, flash-attn 2.8.x)가 `num_splits=0`일 때 쓰는 휴리스틱*이다: 배치 × 질의 헤드 × m-블록 수가 SM 수의 0.8배를 넘으면 분할을 하지 않고 돌아가며, 요청별 KV 길이를 보지 않는다. 이 조기 반환이 혼합 길이 손실의 직접 원인이므로 정의에 그 규칙과 버전을 명시해야 한다. 같은 이유로 어떤 서빙 엔진이 이 문제를 그대로 물려받는지도 적어야 한다: vLLM v1의 FlashAttention 백엔드는 전체 CUDA Graph 모드가 아니면 `num_splits=0`(라이브러리 휴리스틱)을 쓰고, CUDA Graph 모드에서만 최대 분할 수를 16으로 고정한다(중간 버퍼 메모리 때문에 그때만 켠다는 주석). 즉 운영 엔진에서도 문제가 재현될 조건이 있고(PLAN §2 5번), 반대로 FlashInfer 백엔드를 쓰는 엔진에서는 애초에 생기지 않는다.
2. **"답이 유지된다"는 전제를 경험적 검증으로 바꿔 적어야 한다.** 분할 수가 달라도 연산은 같지만 부동소수점 합산 순서가 달라 로짓이 bf16 간격 단위로 흔들리고, 드물게 토큰이 갈린다. 10월 2일 대조군의 `clear` 사건은 로짓 동점이 아니라 앞 문맥의 어느 자리를 복사할지 정하는 attention 점수의 동점이 갈린 경우였고, 커널 탐침은 구현 오류가 아님을 보였다. 따라서 정의는 "수학적으로 같은 연산(반올림만 다름)이며, 생성 토큰의 동일성은 분기 사건 수와 동점 분류로 보고한다"가 정확하다. "답이 바뀌지 않는다"는 단정은 쓰지 않는다.
3. **"시뮬레이션 기반 선택"은 과장이다.** 선택 정책(테이블·모델·혼합)은 전부 실측과 실측으로 맞춘 성능 모델에서 나오고, Accel-Sim은 미보정(1.05~3.06배)이라 선택에 기여하지 않는다. 시뮬레이터의 실제 역할은 "SM 수·대역폭이 바뀌면 같은 현상이 어떻게 되는가"의 설명·민감도 분석과 GPGPU-Sim 축소 커널의 정성 재현이다. 제목과 §0의 "시뮬레이션 기반 선택"을 "실측·성능 모델 기반 선택 + 시뮬레이션 기반 원인 설명"으로 고치는 편이 심사에서 안전하다.
4. **문제의 실무적 크기가 측정돼 있지 않다.** 혼합 길이 손실은 "긴 요청 소수 + 짧은 요청 다수"에서 크고 균일 배치에서는 없다. 실제 트래픽에서 그런 배치가 얼마나 자주 생기는지(예: 공개 요청 길이 분포로 연속 배치를 모사했을 때 휴리스틱이 조기 반환하는 step의 비율)를 숫자로 보이지 않으면 "문제가 중요하다"는 주장은 합성 시나리오에 머문다. GPU 없이도 할 수 있는 분석이다.

정의의 핵심 질문을 한 줄로 다시 쓰면: **"커널을 바꾸지 않고 기존 커널의 분할 수만 밖에서 고를 때, 혼합 길이 배치의 손실을 얼마나 되찾을 수 있고 그 한계는 어디인가."** 지금 §0에는 이 "커널을 바꾸지 않는다"는 제약과 그 대가가 빠져 있는데, 이것이 관련 연구와의 경계선이다(§3).

**같은 날 오후 후속.** 미비점 2는 정책 캐시 유지 규약 재측정으로 해소됐다(혼합 1.090배 ≈ 모델 1.091배 > 테이블 1.086배, 노트 §3b). 미비점 4의 커널 부분은 측정됐다(FlashInfer CUDA-core ≈ 최선 FA2, 노트 §8); 전체 모델 백엔드 비교는 남았다. 미비점 8의 엔진 guard는 고쳤다. vLLM 재현(노트 §9)은 증상은 보였지만 원인이 분할 수 휴리스틱이라는 점은 그 엔진에서 확인되지 않았으므로, §1 1번의 "어떤 엔진이 이 문제를 물려받는가"는 vLLM 0.31에 대해서는 아직 답이 없다.

## 3. 같은 문제를 다른 연구·시스템은 어떻게 푸는가, 우리와의 차이

| 접근 | 무엇을 바꾸는가 | 혼합 길이 처리 | 우리 작품과의 관계 |
|---|---|---|---|
| **Flash-Decoding / FlashAttention-2 decode 경로** (Dao 외) | KV를 조각으로 나눠 병렬 계산 후 log-sum-exp로 결합 | `num_splits=0`이면 배치·헤드·m-블록 수와 SM 수만 보는 휴리스틱; 요청별 길이는 보지 않음 | **우리가 고르는 설정값의 정의와 기본 휴리스틱.** 우리는 이 커널을 그대로 쓰고 인자만 바꾼다 |
| **FlashInfer** (Ye 외, MLSys 2025) | attention 엔진 교체: 블록 희소 KV 형식 + JIT 템플릿 + plan/run 구조 | **CPU의 plan 단계에서** 각 요청의 KV를 최대 크기 L_kv의 조각으로 나누고, 우선순위 큐로 CTA별 비용 불균형이 최소가 되게 조각을 배정(탐욕적 bin-packing). 격자 크기가 고정돼 CUDA Graph와 호환, plan 비용은 여러 층에서 재사용해 상각. 길이 분포가 치우친 배치에서 FlashAttention 커널을 크게 앞선다고 보고 | **가장 가까운 기존 해법이자 상한.** 커널 내부 스케줄링으로 불균형을 없애므로 분할 수를 고를 필요 자체가 없다. 우리 작품의 존재 이유는 "엔진을 바꾸지 않고 FA2의 인자만 골라 이 이득의 얼마를 얻는가"이며, 그 답(격차의 크기)을 아직 재지 않았다(미비점 4) |
| **LeanAttention** (Microsoft, MLSys 2025) | decode attention의 실행 흐름 재설계: online softmax를 reduction으로 보고 stream-K 방식으로 SM에 균등 분배 | 길이가 다른 요청(ragged batch)을 포함해 작업을 SM 수로 균등 분할 | 역시 커널 수준 해법. 분할 수라는 이산 설정이 아니라 연속적 분할. 우리와 같은 문제 인식(긴 문맥·작은 배치에서 SM 미활용)에서 출발 |
| **FlashDecoding++** (Hong 외, 2024) | unified max softmax, flat GEMM, 입력·하드웨어별 휴리스틱으로 실행 방식 선택 | 실행 방식의 휴리스틱 선택 | "모양을 보고 실행 방식을 고른다"는 점이 우리와 같다. 다만 선택 대상이 자기 커널이고, 선택 근거가 실측 테이블·성능 모델이 아니다 |
| **vLLM (FlashAttention 백엔드)** | 엔진. FA2 커널 사용 | 전체 CUDA Graph 모드에서만 최대 분할 수 16 고정, 그 외는 라이브러리 휴리스틱 | **문제가 그대로 남아 있는 운영 환경.** 고정 16은 균일 배치에서 중간 버퍼 낭비를 감수하는 선택이고, 길이 분포를 보는 정책은 아니다. PLAN §2 5번(vLLM 재현)이 이 표의 근거가 된다 |
| **Vidur** (MLSys 2024), **LLMServingSim** (2024) | 서빙 시스템 시뮬레이터: 연산자 프로파일 + 예측 모델(Vidur, 지연 오차 <9%), 가속기·서빙 SW 공동 시뮬레이션(LLMServingSim, 오차 <14.7%) | 배치 구성·배포 설정 탐색 | 우리 성능 모델은 attention 커널 하나의 런치 지오메트리·바이트·FLOPs 모델로 훨씬 좁고, 쓰임새가 "실행 중 분할 수 선택(테이블과 혼합)"이다. 평가 기준도 지연 오차가 아니라 **선택 손실(regret)**이다 |
| **Accel-Sim / GPGPU-Sim** | 사이클 수준 GPU 시뮬레이터 | — | 우리는 설명·민감도 분석에만 쓴다(§1 3번) |
| **커널 자동 튜닝** (TVM/Ansor, Triton autotune, cuBLAS 휴리스틱) | 오프라인에서 모양별 최적 구현 선택 | 모양별 탐색 | 우리는 (a) 실행 중 매 step, (b) 실측 테이블 + 성능 모델의 혼합, (c) 생성 토큰 동일성까지 검증한다는 점이 다르다 |

**차별점으로 쓸 수 있는 것** — 새 커널이나 새 시뮬레이터가 아니라는 전제에서:
1. **기존 커널·기존 엔진을 바꾸지 않는 외부 선택**의 효과와 한계를 끝까지 측정했다: 커널 손실(12.53배/3.84배) → 전체 모델 TPOT(1.81배) → 토큰 동일성 → 그리고 "안 되는 곳"(균일 배치 attention 19.2%, 선택 비용이 이득을 넘는 요청 도착 조건)까지. 커널 수준 해법(FlashInfer·LeanAttention)과의 격차를 재는 것이 이 차별점의 마지막 조각이다.
2. **실측 테이블과 성능 모델을 섞는 선택과 그 평가 방법**: leave-one-out 손실(δ=0.2에서 최악 1.97/7.54/10.90%), 실생성에서 테이블과 갈리는 조건의 attention 이득(3.31→3.00 ms/step). 이 조합은 위 표의 어느 시스템도 하지 않는 일이지만, 실행 중 비용(미비점 2)을 풀기 전에는 "오프라인 테이블 생성기"로서의 가치가 더 크다.
3. **출력 동일성의 정직한 지표**: 토큰 일치율 대신 분기 사건 수 + bf16 동점 분류 + 같은 KV 상태의 커널 탐침. 서빙 시스템 논문들이 보통 생략하는 검증이며, 심사에서 "답이 바뀌지 않느냐"에 대한 답이 된다.
4. **GPU 없이 재계산되는 근거**(verify 86개, 번들 해시, 대시보드). 재현성은 차별점이라기보다 졸업작품의 신뢰 근거다.

솔직한 위치: 이 작품은 FlashInfer류와 경쟁하는 해법이 아니라, **"엔진을 바꾸지 못하는 환경에서 기존 커널의 설정만으로 얻는 이득과 그 한계를 실측·모델·시뮬레이션으로 정량화하는 진단·선택 파이프라인"**이다. 보고서의 기여 문장은 이 범위를 넘지 않아야 한다.
