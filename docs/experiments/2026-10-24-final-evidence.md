## §1 고정 분할 수 기준선 (2026-10-24)

질문: **동적 선택 대신 split-KV 분할 수 하나(예: 항상 16)로 고정하면 안 되는가?** 이 절의 격자 분석은 GPU 없이 번들(`demo_data/hw_4090/*_paged`)에서 다시 계산되고(`make verify`의 `fixedsplit.*` 항목), 엔진 안 실생성은 GPU 대기열 항목 01이 잰다(아래 "실생성" 참고).

**방법.** 페이지 KV, cold L2 격자의 모든 셀에서 FA2 decode 커널의 `num_splits`를 1, 2, 4, 8, 16, 32, 64, 128로 고정한 시간과, FA2 휴리스틱(`num_splits=0`)의 시간을 읽는다(분할 수 1은 `fa2_paged`). 셀마다 regret = 시간(정책) / 시간(기준)이고, 기준은 **최선 FA2 분할**(`fa2_best`, 측정한 FA2 분할 중 가장 빠른 것 = 분할 수만 고르는 선택기의 상한)이다. FlashInfer 변형이 측정된 32K·64K 격자에는 전체 최선(FlashInfer 포함) 대비 값도 따로 구했다. `fa2_best`는 정의상 regret 1이므로 표의 "선택기" 행은 상한이지 측정된 정책이 아니다. 단일 s\*는 혼합+균일 합집합에서 최악 regret을 최소화하는 분할 수이고(동률은 p90), 합집합은 32K 혼합 162셀과 32K 균일 49셀(둘 다 cold)이다. 구현은 `kernelscope/analysis/dispatch.py`의 `fixed_split_table`·`fixed_split_summary`·`best_fixed_split`이다.

**해석 (격자 분석 범위 안에서).**

1. **"항상 8(또는 16)"은 약한 기준선이 아니다.** 이 격자들에서 단일 분할 수 8은 FA2 휴리스틱(최악 3.981배, 108셀이 1.25배 초과)이 잃는 것의 거의 전부를 되찾는다: 혼합 길이 중앙값 1.436배 → 1.010배, 64K 최악 5.183배 → 1.009배. 따라서 이 작품의 문제 정의 "정적 기본값(FA2 휴리스틱)이 혼합 길이 배치에서 틀린다"는 유지되지만, "그래서 동적 선택이 필요하다"는 주장은 **이 격자만으로는 성립하지 않는다.** 고정 분할 수 하나가 커널 수준에서 분할 수 선택기 상한 대비 중앙값 1%, 최악 13% 안에 있다.
2. **동적 선택이 이 격자 위에서 줄일 수 있는 것은 고정 8의 잔여 손실이다.** 합집합에서 중앙값 1.010배, p90 1.034배, 최악 1.127배(최악 셀은 균일 B=8, KV 512로, 최선 커널이 31 µs인 가장 작은 쪽이다). 혼합 길이만 보면 최악 1.042배다. 이 값은 모델이나 테이블을 맞추지 않은 고정값의 값이고, 단일 s\*를 8개 후보 중에서 같은 셀로 고른 데서 오는 약한 선택 편향(1개 모수)만 있다. 반면 선택기 상한(1.000배)은 같은 셀을 보고 정한 in-sample 값이라 held-out 정책의 값(leave-one-out 최악 손실 PLAN §1 ③)과 직접 비교할 수 없다.
3. **고정 분할 수가 틀리는 조건.** 분할 1·2·128은 고정으로는 쓸 수 없다(합집합 최악: 분할 1은 4.861배, 분할 2는 2.462배, 분할 128은 2.432배). 분할 16은 cold 균일의 짧은 KV·작은 배치에서 최악 1.162배다. warm 균일(결과 6)에서는 분할 8도 1.712배까지 잃으므로 warm 캐시 상태를 가정하는 서빙에서는 이 결론이 바뀐다.
4. **격자의 범위 한계.** 모두 Qwen3-4B 헤드 구성(H_q=32, H_kv=8)의 S1 격자와 한 GPU(RTX 4090)이며 KV 길이는 8K~64K 혼합, 512~32K 균일뿐이다. 실제 서빙의 길이 분포(트레이스 재생)에서 어떤 값이 나오는지는 커널 격자로 알 수 없다. 출력 동일성(분할 수가 바뀌면 bf16 반올림 차이가 생긴다)은 격자 분석으로 볼 수 없고 아래 실생성과 §4 이후의 몫이다.

**해석 (핵심 질문에 대한 답, 엔진 실생성 범위 안에서).**

1. **고정 분할 수는 혼합 길이에서 table과 같은 이득을 얻는가 → 이 시나리오들에서는 그렇다.** 32K 혼합 길이(고정 16 1.804배 대 table 1.813배, 고정 8은 이상치를 빼면 1.811배), 요청 도착(고정 8 1.178배 대 table 1.173배), 64K(고정 8 2.443배 대 table 2.448배) 모두 TPOT 이득이 table의 ±1% 안이다. 격자 분석(위)의 결론이 엔진에서도 확인된다.
2. **균일 길이·도착 조건에서 얼마나 잃는가 → TPOT로는 거의 잃지 않는다.** 균일 길이에서 고정 8은 0.2%, 고정 16은 1.0% 잃고, 도착 조건에서는 table과 같거나 낫다. 격자의 최악 셀(고정 8 균일 B=8, KV 512, 1.127배)에 해당하는 step은 이 시나리오에 없다.
3. **출력은 어떤가 → 균일 길이에서 고정 분할만 토큰이 바뀐다.** table은 휴리스틱이 맞는 곳에서 휴리스틱을 그대로 두므로 토큰이 같지만, 고정 8·16은 균일 길이에서 6곳 갈린다(대부분 bf16 동점, 1곳은 clear로 기존 대조군과 같은 자리).
4. **정리: 고정 설정으로 충분한 조건 / 동적 선택이 필요한 조건.**
   - 충분한 조건(이 GPU·모델·시나리오에서 측정): 32K·64K 혼합 길이와 요청 도착에서 TPOT 이득이 필요할 때. 고정 8 또는 16 하나로 table과 같은 이득이다.
   - 동적 선택이 값을 하는 조건(이 엔진 실험에서 직접 보인 것): 휴리스틱이 이미 맞는 균일 길이에서 **출력이 휴리스틱과 같아야 할 때**(table 분기 0곳 대 고정 6곳). TPOT 이득 면에서 동적 선택의 우위는 이 실험에서 확인되지 않았다.
   - 이 실험이 보지 못한 것: 엔진에서의 warm 캐시 상태(커널 격자에서는 warm 균일 고정 8이 최악 1.712배), 다른 헤드 구성·GPU, 실제 트래픽의 길이 분포(트레이스 재생 §2의 모델 예측에서는 BurstGPT류에서 고정 8이 휴리스틱보다 최대 5.7% 손해), table 정책의 선택이 혼합 길이에서 사실상 고정 16이었다는 점(동적 선택이 "다른 곳"을 골라야 하는 시나리오는 세 개 안에 없다). 반복 3회, 각 조건 1개 시나리오이므로 일반화하지 않는다.
   - 보고서의 정당화 문구는 사용자 결정 필요(P1a 보고와 같음): "고정 8(16)이 강한 기준선이며, 동적 선택은 출력 보존·측정 격자 밖 조건(warm, 다른 구성)에서의 안전성을 사는 것"이 이 근거와 맞는다.

## §2 부하 스윕과 고정 분할 수의 trace replay 채점 (2026-10-24, 단계 P2a)

질문: 문제 범위 노트 §1의 "Azure conv ×1에서 step 13.5%가 regret ≥ 1.25"는 도착 배율 하나에서의 값이다 — **왜 ×1인가?** 그리고 분할 수를 하나로 고정하면 같은 trace에서 어디에 서는가? GPU 없이 trace replay(`scripts/traffic_replay.py`, 설정은 기존과 같다: KV 10 GiB = 72,817 토큰, 배치 상한 64, step 30 ms, cold L2, Qwen3-4B 헤드 구성 32/8)를 도착 배율 21개로 돌렸다. 이 절의 모든 수치는 **적합한 성능 모델의 예측**이다(커널 시간 오차 2.3~12.3%); prefill은 즉시, step 시간은 배치와 무관하게 30 ms라는 §1의 단순화가 그대로다. 실측이 아니다.

**재현성 점검.** 기존 실행과 같은 배율 8개(conv ×0.5·1·2, code ×4·8·16, BurstGPT ×50·100)를 새 폴더에 다시 돌려 `losses` 필드와 step 수가 `demo_data/traffic/`과 한 자리도 다르지 않음을 확인했다(`make verify`의 `sweep.repro.*`). 첫 실행 폴더(`traffic_sweep_20261024_failed_20261024T2230`)는 부하 필드 이름만 바꾸려고 같은 설정으로 다시 돌린 것이고 두 실행의 손실·고정 분할 수치는 모두 같다.

**방법.** 측정 항목: 평균 배치, 휴리스틱이 분할하지 않는 step 비율, regret(= 휴리스틱 예측 시간 / 후보 {휴리스틱, 분할 2·4·8·16} 중 최선) ≥ 1.1·1.25·1.5인 step 비율, 전체 attention 시간 비(휴리스틱/최선 = "휴리스틱 비"). 고정 분할 수 S의 채점은 같은 후보 예측을 쓴다: "항상 S" 정책의 attention 시간 합 / 최선 시간 합 = **S/최선**, S 시간 합 / 휴리스틱 시간 합 = **S/휴리스틱**(< 1이면 S 고정이 이긴다). S는 §1에서 고른 8과 16(및 2·4). 최선은 후보 5개 안의 최선이므로 S ∈ {2,4,8,16}의 S/최선은 1 이상이다. 부하는 평균 배치 외에 재생기가 내는 **큐 대기**(요청 도착부터 admission까지: 배치 상한이나 KV 페이지가 찰 때 기다림)로도 적는다 — 이 재생기에서 큐 대기가 1초를 넘는 요청이 늘기 시작하는 곳이 서버가 감당하는 부하의 끝이다. "활성 비율"은 요청이 하나 이상 decode 중인 시간 비율이지 연산 점유율이 아니다(step 시간이 상수라 연산 점유율은 모델에 없다).

### 해석 1 — regret ≥ 1.25 step 비율이 평균 배치에 대해 봉우리 모양인 이유

Azure conv: 평균 배치 8.7 → 17.4 → 26.1 → 34.8 → 43.4 → 47.0에서 비율은 0.4% → 2.4% → 11.6% → **13.5%** → 5.9% → 4.1%이고, 평균 배치가 KV 예산에 닿는 47 근처(×1.5 이후)에서 4.1~4.2%로 평평해진다. 봉우리는 서로 반대로 움직이는 두 인자의 곱이다.

- **문턱(B ≥ 26).** 휴리스틱은 `배치 × KV 헤드 × m-블록 ≥ 0.8 × (2 × SM 수)`이면 분할 없이 돌아간다. 4090(SM 128)·KV 헤드 8에서 `B × 8 ≥ 204.8`, 즉 **B ≥ 26**이다. B < 26에서는 휴리스틱이 스스로 분할하므로 regret ≥ 1.25가 거의 없다: conv ×1·×2의 step을 합쳐 B 13~25에서 0.5%, B 1~12에서 0%. 이 문턱이 왼쪽 경사를 만든다 — B ≥ 26인 step 비율이 ×0.5에서 6.2%, ×0.75에서 53.6%, ×1에서 89.5%로 오른다.
- **희석(CTA 수).** B ≥ 26이 되고 나면 regret이 큰 step은 오히려 줄어든다. B ≥ 26인 step 중 regret ≥ 1.25 비율: ×0.5 30.4%, ×0.75 21.5%, ×1 15.0%, ×1.25 6.0%, ×2 4.2%(참고: B ≥ 26인 step 중 code ×16은 20.0%). 같은 trace를 배율만 바꿔 재생한 것이라 배율의 효과가 아니라 **배치 크기의 효과**임을 step 단위로 확인했다: conv ×1과 ×2의 step을 합쳐 B별로 보면 B 26~29에서 30.3%, 30~34 16.4%, 35~39 14.5%, 40~44 8.8%, 45~49 3.8%, 50~64 1.2%다(`demo_data/traffic_sweep/batch_bins.json`). 분할하지 않는 launch는 `B × KV 헤드`개의 CTA를 내고, 긴 요청 하나의 CTA가 끝날 때까지 나머지가 기다리는 load imbalance가 손실의 원인이다(문제 범위 노트 §1, 부하 불균형 기전). 짧은 요청이 늘어 CTA 수가 SM 수의 몇 배가 되면 짧은 CTA가 긴 CTA의 꼬리 동안 다른 SM을 계속 채워 꼬리가 가려진다. 이 절은 그 희석을 모델 예측의 배치별 regret으로 보인 것이지 별도 커널 실험으로 분리한 것은 아니다. 길이 불균형(len_max/len_mean)은 부하가 늘수록 오히려 커지므로(B ≥ 26 step 평균 ×0.5 2.4 → ×2 2.9) 희석 말고 길이 분포 쪽 설명은 맞지 않는다.
- **봉우리의 위치.** 문턱 인자는 평균 배치 ≈ 26 부근(×0.75)에서 포화하고 희석 인자는 계속 줄어서, 곱은 ×0.75~1에서 최대(11.6%~13.5%)다. ×1은 결과적으로 이 봉우리의 꼭대기와 같고 임의로 고른 값은 아니지만, 배율이 정당한지는 아래 부하 기준이 따로 가른다.

**부하 기준(큐 대기).** conv ×0.75까지는 대기 p99가 한 step(0.03 s)이고, ×1에서 p99 3.7 s·대기 > 1 s 요청 5.5%로 큐가 생기기 시작하며, ×1.25부터는 p50 대기도 2.6 s이고 ×1.5 이후는 대기가 trace 길이에 비례해 늘어난다(이 GPU 설정으로 감당하지 못하는 부하; 이때 배치는 KV 예산이 정한 47 근처로 고정되므로 ×1.5~×4의 통계가 서로 거의 같다). 즉 **봉우리는 서버가 감당하는 부하의 끝 가장자리**(×0.75~×1)에 있고, 그보다 오른쪽(과부하)에서는 regret ≥ 1.25가 4%대로 가라앉는다. "SLO 근처"를 큐 대기 p99 ≲ 4 s로 읽으면 conv에서 이 값은 11.6~13.5%(×0.75~×1)이고, 대기를 1 s 안으로 엄격하게 잡으면 ×0.75의 11.6%다. 이 절은 SLO 값을 정하지 않는다 — 임계값은 사용자 결정 사항이다.

Azure code(프롬프트가 conv보다 길어 KV 예산이 먼저 찬다): 평균 배치가 17.8에서 27.4로 오르며 8.0% → 14.1%로 오르고 ×16 이후 27.4에서 14.0~14.1%로 고원이다(과부하, 대기 p99 57 s 이상). 추정이지만 긴 프롬프트가 KV 예산을 먼저 채워 배치가 26을 간신히 넘는 선에서 멈추므로 희석이 약한 채 고원이 되는 것으로 읽힌다(이 해석은 별도로 분리 확인하지 않았다). code는 감당 가능한 부하(×2, 대기 p99 2.8 s)에서 4.1%이고 큐가 생긴 뒤에 문제가 커진다 — 배치가 상한 64보다 한참 낮은 7.9에서 이미 대기가 생기므로 큐를 만드는 것은 배치 상한이 아니라 KV 페이지다. BurstGPT: 짧은 프롬프트라 어느 배율에서도 regret ≥ 1.25가 0.1~0.3%이고 휴리스틱 비도 1.008~1.051로 작다 — 배율을 키워도 문제가 생기지 않는다.

정리: **"13.5%"는 스윕에서 가장 큰 conv 값이면서 서버가 큐 없이 감당하는 부하의 끝에 해당한다.** 21개 실행 중 최댓값은 code ×16 이후의 14.0~14.1%이지만 그 부하에서는 큐가 이미 폭주해 있다. 보고서에는 "조건부 문제: 평균 배치가 문턱(26)을 넘는 부하 구간에서 conv는 최대 13.5%, 과부하 포화 시 4%대, 짧은 프롬프트(BurstGPT)는 어느 부하에서도 0.3% 이하"라고 쓴다.

### 해석 2 — 고정 분할 수는 trace 전체에서 어디에 서는가

- **S=8 고정은 휴리스틱이 나쁜 구간에서 대부분을 되찾는다.** 최선 대비 attention 시간: conv ×1에서 휴리스틱 1.119 → S=8 1.034 (휴리스틱과 최선 사이 격차의 71%를 되찾음), conv ×0.75 63%, conv ×2 64%, code ×16 1.136 → 1.005(96%). S=8/휴리스틱은 전체 21개 실행에서 0.885(code ×16)~1.057(BurstGPT ×400)이다.
- **그러나 휴리스틱이 이미 최선에 가까운 trace에서는 S=8이 손해다.** BurstGPT에서 휴리스틱 비는 1.008~1.051인데 S=8은 최선 대비 1.049~1.065라서 S=8/휴리스틱이 1.007~1.057(×100 이상에서 1.04~1.06)이다. 저부하 conv ×0.25(평균 배치 8.7)도 S=8/휴리스틱 0.993으로 이득이 없다. S=16은 이보다 일관되게 나쁘다: 최선 대비 conv 1.086~1.124, BurstGPT 1.107~1.128. 분할 수가 클수록 짧은 요청 위주의 step에서 낭비가 커진다.
- **step 층화(배치 B < 26 대 ≥ 26).** conv ×1: B ≥ 26 step에서 휴리스틱/최선 1.125, S=8/최선 1.035; B < 26 step에서 휴리스틱 1.025, S=8 1.023. 즉 S=8의 이득은 B ≥ 26 쪽에서만 나오고 B < 26 쪽에서는 휴리스틱과 같은 수준이다. BurstGPT ×100은 B ≥ 26 step에서 휴리스틱 1.012, S=8 1.064(S=8이 6% 손해), B < 26 step에서 휴리스틱 1.038, S=8 1.041.
- **단일 step의 최악은 크다.** S=8 고정의 step별 최악 regret은 1.16~1.36(code ×8에서 1.360)이고 regret ≥ 1.25인 step은 conv ×0.25 0.3%, BurstGPT ×25 0.5%, code ×2 1.3%, 과부하 구간에서는 0%다. 휴리스틱의 step별 최악(conv ×1 2.19)보다는 작지만 §1의 32K 격자(S=8 최악 1.042·1.127)보다 크다. 격자에 없는 짧은 KV·작은 배치 step에서 분할이 낭비인 경우라고 추정하지만 이 절은 그 step을 분리해 확인하지 않았다.
- **동적 선택과의 간격은 작다.** 후보 5개 안의 per-step 최선은 정의상 1.000이고 S=8과의 간격은 trace 평균으로 0.5~6.5%다. 즉 이 trace 재생이 보여주는 정당화는 "동적 선택이 고정 8보다 몇 배 낫다"가 아니라 **휴리스틱 → 고정 8의 이득(최대 11.5%)이 BurstGPT 같은 짧은 프롬프트 trace에서는 −5.7%까지 거꾸로 되고, 동적 선택은 두 경우 모두 최선**이라는 것이다. 이 최선은 성능 모델의 예측 위의 최선이며 실제로 고르는 정책(table·hybrid)의 손실은 §1과 문제 범위 노트 §3에서 실측으로 따로 본다.

## §4 헤드 구성·GPU별 분할 없음 임계 (2026-10-28, 야간 P2c 미실행분)

**질문.** "배치 26 이상이면 분할 없음"은 Qwen3-4B(KV 헤드 8)·RTX 4090(SM 128)의 값이다. 다른 GPU·모델에서는 이 경계가 어디인가.

**규칙(원문 확인).** flash-attn v2.8.3.post1(`/home/skkai/accelsim/flash-attention`, 커밋 `a8aa52b1`)의 `csrc/flash_attn/flash_api.cpp:317`은 `num_splits_heuristic(batch_size * num_heads * num_m_blocks, num_sm * 2, num_n_blocks, 128)`을 호출하고("128 threads per block"이라 SM 수를 2배), 휴리스틱은 첫 인자가 `0.8 * num_SMs` 이상이면 1을 돌려준다(같은 파일 263행, 리포 이식 `kernelscope/model/geometry.py::num_splits_heuristic`). decode에서 GQA이면 `flash_api.cpp:1278`이 질의 그룹을 seqlen 차원으로 옮겨 `num_heads = num_heads_k`가 되고, `num_m_blocks = ceil(그룹 수 / 64)`는 KV 헤드당 질의 헤드가 64개 이하인 모든 모델에서 1이다. 따라서 임계 배치는 B* = (B·H_kv ≥ 0.8·2·SM을 만족하는 가장 작은 B)이고 GPU의 SM 수와 GPU당 KV 헤드 수만으로 정해진다. 텐서 병렬 t를 쓰면 GPU당 KV 헤드가 H_kv/t로 줄어든다. 이 표는 **라이브러리 규칙의 계산이지 실측이 아니다.** Hopper에서 FlashAttention-3를 쓰면 decode 경로와 휴리스틱이 다르므로 H100 행은 FA2 기준이다.

**입력과 출처.** `demo_data/thresholds/no_split_threshold.json`. SM 수: L4 58·L40 142(NVIDIA Ada GPU Architecture 백서 부록 D·C), RTX 4080 16GB 76·RTX 4090 128(같은 백서 표 3·표 1), RTX 3090 82(GA102 백서 v2 표 9), A100 108(A100 백서), H100 PCIe 114·SXM5 132(NVIDIA Hopper Architecture In-Depth). 백서 PDF는 2026-10-28에 내려받아 해당 표의 SM 행을 확인했다. 모델 헤드 구성은 로컬 Hugging Face 캐시의 config.json: KV 헤드 8 — Qwen3-1.7B·4B-Instruct-2507·8B, DeepSeek-R1-Distill-Llama-8B, kanana-1.5-8b-instruct; KV 헤드 4 — DeepSeek-R1-Distill-Qwen-7B, A.X-4.0-Light(이 리포 S2 격자의 28/4와 같다). 모두 헤드 차원 128, sliding window 미사용.

**표: 분할 없음이 시작되는 최소 배치 B\***(`kernelscope/analysis/thresholds.py::threshold_table`)

|---|---:|---:|---:|---:|---:|

| RTX 4080 16GB | 76 | 16 | 31 | 61 | 122 |
| RTX 3090 | 82 | 17 | 33 | 66 | 132 |
| A100 | 108 | 22 | 44 | 87 | 173 |
| H100 PCIe | 114 | 23 | 46 | 92 | 183 |
| RTX 4090 | 128 | 26 | 52 | 103 | 205 |
| H100 SXM5 | 132 | 27 | 53 | 106 | 212 |
| L40 | 142 | 29 | 57 | 114 | 228 |

KV 헤드 2·1 열은 KV 헤드 8 모델을 텐서 병렬 4·8로 나눈 경우다.

**실측 launch와의 대조.** `demo_data/hw_4090/`의 decode 휴리스틱 실행 기록(10개 측정 집합, 헤드 구성 32/8과 28/4, cold·warm)은 785건이다. 분할하면 분할 커널과 결합 커널이 함께 실행되므로 launch 수가 2다. 규칙으로 계산한 분할 여부와 기록된 launch 수는 785건 모두 일치했다(규칙상 분할 426건, 분할 없음 359건). 즉 RTX 4090의 두 헤드 구성에서 경계 B* = 26·52가 실제 커널 실행과 맞는다(`kernelscope/analysis/thresholds.py::launch_agreement`).

**해석.** KV 헤드 8인 단일 GPU 서빙에서는 조사한 8종 GPU 모두 B* = 12~29로, 연속 배치가 흔히 도달하는 크기에서 분할이 꺼진다. 따라서 "긴 요청이 섞이고 배치가 B* 이상"이라는 취약 조건은 RTX 4090만의 현상이 아니다. SM이 적은 GPU일수록 더 작은 배치에서 시작된다. 반대로 KV 헤드가 적은 모델이나 텐서 병렬로 GPU당 KV 헤드가 줄면 B*가 커져(KV 헤드 2: 47~114) 같은 문제가 더 큰 배치에서만 나타난다. 분할 없음 구간 밖(B < B*)에서도 휴리스틱이 최대 길이만 보고 분할 수를 정하는 문제는 남는다(§3의 B < 26 step).

## §5 혼합 정책 δ 민감도 (2026-10-28, 야간 P2d 미실행분 중 δ 부분)

**질문.** 혼합 정책의 δ = 0.2는 임의로 고른 값인가. (같은 단계의 신뢰구간 과제는 이번에도 하지 않았다.)

**방법.** `scripts/evaluate_hybrid.py`와 같은 leave-one-out 평가(`kernelscope/model/hybrid.py::evaluate`)를 δ = 0, 0.01, …, 1.00의 101개 점에서 반복했다. 검증 집합은 서빙에 쓰는 cold 상태의 V1(균일 보간, 66개 조건), V5(미학습 헤드 구성, 98개), V6(혼합 길이, 219개)이다. 기록된 실측(`demo_data/hw_4090`)만 쓰므로 GPU가 필요 없다. δ = 0은 성능 모델 정책, δ가 매우 크면 조회 테이블 정책과 같다.

**결과.** 최악 손실(15%를 넘는 조건 수)

| δ | V1 cold | V5 cold | V6 cold |
|---|---:|---:|---:|
| 0.00 | 24.25% (1) | 66.29% (3) | 24.52% (2) |
| 0.05 | 24.25% (1) | 66.29% (3) | 7.53% (0) |
| 0.10 | 24.25% (1) | 66.29% (3) | 9.78% (0) |
| 0.15 | 1.97% (0) | 24.75% (1) | 10.90% (0) |
| 0.16 | 1.97% (0) | 7.54% (0) | 10.90% (0) |
| 0.26 | 1.97% (0) | 7.54% (0) | 10.90% (0) |
| 0.30 | 3.34% (0) | 7.54% (0) | 10.90% (0) |
| 0.32 | 3.34% (0) | 14.83% (0) | 10.90% (0) |
| 0.33 | 16.86% (1) | 14.83% (0) | 10.90% (0) |

**해석.** 세 집합의 최악 손실이 모두 15% 이내인 구간은 δ = 0.16~0.32이고, 0.01 간격 격자에서 끊김 없이 17개 점이다. 그 안의 0.16~0.26(11개 점)에서는 세 최악값이 δ = 0.2와 똑같이 1.97% / 7.54% / 10.90%다. 즉 0.2는 평탄한 구간 안에 있다. 구간 양 끝에서 기준을 넘기는 것은 각각 한 조건이다. δ = 0.15에서는 V5의 한 조건(24.75%)이, 0.14 이하에서는 V1의 한 조건(24.25%)도 남아 모델이 고른 후보를 테이블이 바로잡지 못한다. δ ≥ 0.33에서는 V1의 한 조건에서 테이블의 오류(16.86%)가 들어온다. 2026-09-26 노트는 상한 쪽을 "0.35 이상"으로 적었으나, 0.01 격자에서는 0.33부터 V1이 기준을 넘는다(통과 구간 0.16~0.32는 같다). warm 상태 V1은 어떤 δ에서도 기준을 넘는다(2026-09-26 노트와 같은 결론, 이 표에서는 제외).

## §6 trace replay 채점의 실측 검증 (2026-10-24, 항목 02)

**질문.** 문제의 크기 "Azure conv ×1에서 decode step의 13.5%가 attention 시간을 1.25배 이상 잃는다"는 성능 모델(surrogate)이 채점한 값이다. 표본 셀을 같은 하네스로 실측해 그 채점이 얼마나 맞는지 본다. (모델 예측과 실측을 구분해 적는다.)

**설계.** `scripts/sample_replay_cells.py`가 trace replay의 고유 길이 구성(256 토큰 페이지로 올린 길이 벡터)을 모델이 예측한 regret 층(<1.1, 1.1–1.25, 1.25–1.5, ≥1.5)별로 뽑았다: Azure conv ×1은 층마다 25개(100셀), Azure code ×16은 층마다 10개(≥1.5는 모집단이 1개라 1셀, 31셀). 시드 0, 길이 벡터는 admission 순서를 유지한다. 각 셀을 `kernelscope bench`(cold L2 flush, paged KV, fp16, H_q=32·H_kv=8·d=128, warm-up 10, 30회 중앙값)로 FA2 휴리스틱(`num_splits=0`)과 분할 2/4/8/16에 대해 쟀다(2회 독립 측정). 셀의 실측 regret = 실측 휴리스틱 시간 / 다섯 변형 중 최선의 실측 시간(모델이 쓰는 후보 집합과 같다). 한 셀은 그 층의 `stratum_steps / 표본 수`개 replay step을 대표하도록 가중해 step 모집단 값을 추정한다. 층 경계가 모델의 예측이라는 점이 곧 검증 대상이다. 95% 구간은 층 안에서 셀을 복원 추출한 부트스트랩 2,000회(시드 0).

**실행 기록.** 시도 1은 첫 `bench`가 `OSError: File name too long`으로 죽었다(B≥36 셀의 workload key가 parquet 파일명 255바이트를 넘음; GPU 점유 문제 아님). 수리 단계가 `kernelscope/results/store.py`의 파일명 태그를 120자로 제한했고(전체 key는 parquet·`summaries.jsonl`에 그대로) 빈 결과 폴더는 `_failed_<시각>`으로 보존했다. 시도 2(00:07~00:09)가 131셀 × 5변형 × 2회를 모두 쟀다. 간섭: 30초 nvidia-smi 기록에 상주 rerun 뷰어와 이 항목의 bench 프로세스뿐 — 간섭 없음. 번들: `demo_data/hw_4090/trace_validation_20261024/{measured_pass1,measured_pass2}.csv`, `cells.json`.

**결과 1 — Azure conv ×1 (100셀, 1회차).** 모델이 regret ≥ 1.25로 예측한 셀은 50개이고 그중 실측도 ≥ 1.25인 셀이 41개다. 표본 기준 precision 0.82, 반대로 실측 ≥ 1.25인 41셀은 모두 예측도 ≥ 1.25였다(recall 1.00; 예측 < 1.25 층 50셀에서는 실측 ≥ 1.25가 0개). 층 비율로 되돌리면 층 가중 precision 0.657(구간 0.466–0.809), recall은 표본에서 양성이 없는 층이 있어 1.00 하나로만 읽히며 이 층들의 표본이 25개씩이라 상한을 단정하지 못한다. 거짓 양성 9셀의 실측 regret은 1.197–1.250 — 문턱 바로 아래다.

| conv ×1 층(예측) | 셀 | 예측 regret 중앙값 | 실측 regret 중앙값 | 실측 ≥ 1.25 | \|예측−실측\| 중앙값 / 최대 |
|---|---:|---:|---:|---:|---|
| < 1.1 | 25 | 1.000 | 1.078 | 0 | 0.036 / 0.202 |
| 1.1–1.25 | 25 | 1.166 | 1.186 | 0 | 0.023 / 0.099 |

층 <1.1의 실측 중앙값 1.078(모델은 휴리스틱이 최선이라고 봄), 층 1.1–1.25는 0/25, 층 1.25–1.5는 16/25, 층 ≥1.5는 25/25. 예측 중앙값 1.326 대 실측 중앙값 1.265(층 1.25–1.5), 예측 중앙값 1.574 대 실측 중앙값 1.426(층 ≥1.5): 모델은 큰 regret을 5~10% 과대 예측하고 작은 regret(휴리스틱이 맞다고 본 셀)을 과소 예측한다.

**결과 2 — step 비율과 attention 시간 비(층 가중).**

| | 모델 예측 | 실측 1회차(95% 구간) | 실측 2회차 | 셀 가중을 키 step 수로 |
|---|---:|---:|---:|---:|

| code ×16: attention 시간 비 | 1.134 | 1.161 | 1.161 | 1.150 |

문장으로: conv ×1은 모델 예측 13.5%에 대해 실측 기준 8.9%(95% 구간 6.3–10.9%)다 — 예측이 구간 밖이고 2회차(9.4%)도 같다. 셀 가중을 같은 키의 step 수로 바꾸면 10.2%(구간 6.5–14.6%)로 13.5%가 구간 안에 들어온다: 표본 설계의 가중 가정에 따라 갈린다. 실측 attention 시간 비는 1.144(구간 1.131–1.156)로 예측 1.119보다 크다: 되찾을 수 있는 attention 시간 비율은 (1 − 1/비)로 예측 10.6%, 실측 12.6%. code ×16은 31셀이라 구간이 넓고(12.5–37.2%) 실측 23.5%가 예측 14.1%보다 크며 recall 0.75(12개 중 9개), precision 0.82(9/11), code ×16의 실측 attention 시간 비 1.161이다.

**결과 3 — 예측 오차와 잡음.** 전 표본(131셀)에서 |예측 regret − 실측 regret| 중앙값 0.048, 최댓값 0.245(상대 오차 중앙값 4.0%, 최댓값 16.9%), 예측·실측 regret의 순위 상관 0.959. 휴리스틱 절대 시간은 실측의 0.867배로 낮게 예측한다(예측 최선 분할이 실측 최선 분할과 같은 변형을 고른 비율 0.710). 같은 셀의 두 측정 회차 사이 실측 regret 차이는 중앙값 0.16%, 최댓값 0.76%로, 위의 모델 오차와 층 경계 효과보다 한 자릿수 이상 작아 측정 잡음은 결론에 영향이 없다.

**결론(한 문장).** 13.5%라는 step 비율은 실측으로는 **약 9%(구간 6.3–10.9%)에 그치고**(가중 방식에 따라 10%까지, 그때 구간은 13.5%를 포함) 문턱 1.25 바로 아래에 모델이 틀리는 셀이 몰려 있어 문턱에 민감하다; 반면 모델의 방향(큰 regret 층 ↔ 실측 큰 regret, 순위 상관 0.959)과 되찾을 attention 시간(예측 1.119 → 실측 1.144)은 지지된다. 보고서에는 "step 비율 13.5%(모델 예측; 실측 표본 추정 9%)"로 병기하고, "attention 시간 10.6%"는 실측으로 12.6%로 같은 방향(약간 더 큼)임을 적는 것이 정직하다 — 문구 선택은 사용자 결정 필요.

**한계.** 표본은 층화이고 층 안 셀 수가 25개라 층별 비율의 구간이 넓다(예측 < 1.25 층의 실측 양성률 0/50은 상한을 정해 주지 않는다). 실측은 cold L2 커널 시간이고 엔진의 실제 L2 상태와 다를 수 있다(§7의 엔진 실측은 이 선택 창에서 모델 예측보다 큰 step 비율을 보였다 — 방향이 반대라 원인은 이 절에서 가리지 않았다). 후보는 휴리스틱과 분할 2/4/8/16뿐이므로 "최선"은 그 안의 최선이다. 이 표본은 conv ×1(117,035 step)과 code ×16(8,647 step)의 trace replay만 대표한다.

## §7 트레이스 구동 end-to-end (2026-10-24, 항목 03)

**상태.** 창 선택·시나리오·모델 예측(CPU)과 엔진 실행(GPU 대기열 항목 03, 2026-10-25 00:12~00:33, 시도 1회에 완료)이 모두 끝났다. 실측은 아래 "실측" 절. 항목 03의 30초 nvidia-smi 기록에는 상주 rerun 뷰어와 이 항목의 프로세스(serve run, 이어서 교사 강제 진단)뿐이라 간섭은 없다.

**목적.** §6(trace replay 채점)과 엔진 실생성의 이득을 같은 부하에서 잇는다. 공개 트레이스(Azure LLM Inference 2023, conv)의 연속 구간을 엔진 시나리오로 바꾸어, 같은 구간에 대한 모델 예측(휴리스틱 대 최선 분할의 attention 시간 비)과 실측 TPOT·처리량·step별 attention 시간을 비교한다.

**창 선택.** `scripts/trace_scenario.py`가 트레이스(19,366건)에서 연속 300개 요청 창을 50건 간격으로 밀며 후보 창 382개를 만들고, 각 창을 replay한다(30 ms 고정 step, prefill 즉시, KV 10 GiB 페이지 예약, 최대 배치 64). 엔진 실행 시간을 줄이려고 출력 길이를 256으로 자르며(출력 상한 256 적용 129건), 프롬프트는 자르지 않는다(상한 적용 0건). 출력 상한 128에서는 사전 탐색한 창 어느 것도 평균 배치 26에 닿지 않아(최대 약 22) 256으로 올렸다. 후보 창 382개 중 17개가 평균 배치 26 이상이고, 그중 모델이 예측한 regret 1.25배 이상 step이 배치 26 이상에서 가장 많은 창(기준 step 589개)을 골랐다: 트레이스의 요청 550..849(트레이스 시각 139.4~188.6 s). 선택 근거 전체는 `demo_data/trace_e2e/selection.json`.

**시나리오.** `scenarios/trace_azure_conv_i550_n300.yaml`: 300개 요청, `arrival_step` = 창의 첫 요청 기준 도착 시각을 30 ms로 나눠 올림, `prompt_len`은 트레이스 값, `max_new_tokens`는 min(트레이스 출력, 256). 프롬프트는 시드 고정 무작위 토큰이다(트레이스는 길이만 제공). 이 창의 최대 프롬프트 4,119 토큰이고 4,096 이상은 4건뿐이다: **트레이스 자체가 짧은 프롬프트 위주여서 이 구간은 32K 혼합 길이 격자와 같은 극단이 아니다.** 문제의 크기를 보는 부하이지 최악 사례가 아니다.

**모델 예측(실측 아님).** 시나리오를 엔진의 논리 step 격자에서 replay하면 1,897 decode step, 평균 배치 26.9이다(replay의 90퍼센타일 36). 성능 모델(cold)이 예측한 휴리스틱 대 최선 분할의 attention 시간 비 1.187 이고, regret 1.25배 이상 step 31.0%, 휴리스틱이 분할 없이 도는 step 67.9%이다. 이 예측의 비교 대상은 모델 후보 5개(`flashdecoding_paged`, 분할 2/4/8/16)의 최선이며 테이블 정책의 선택과 같지 않다. 예측 파일: `demo_data/trace_e2e/predicted.json`(번들), 원본 `serve_4090/trace_e2e_20261024/prediction/`.

- **hybrid·model은 반복 0만 느리다.** 3회 평균 배율이 hybrid 0.969배, model 0.971배(0.971배는 휴리스틱보다 느린 값)인 것은 첫 반복 때문이다: model 반복 0의 TPOT는 43.62 ms인데 반복 1·2는 36.25 ms, hybrid 43.69 ms 대 36.3 ms. 반복 0의 step당 정책 비용이 model 6,461 µs(반복 1은 6.3 µs)이고 결정 캐시 적중률은 65.7%(트레이스의 step 34.3%가 처음 보는 길이 구성)다. model·hybrid는 새 길이 구성마다 성능 모델을 풀어 한 번 결정에 약 19 ms가 든다. table은 같은 첫 반복에서 29 µs/step에 그친다(table은 29 µs). 즉 반복 1·2의 배율(model 1.037배, hybrid 1.035배)은 "같은 트레이스를 한 번 본 뒤"의 값이고, **처음 보는 트래픽에서는 model·hybrid의 결정 비용이 이득을 모두 잃고도 남는다**(이 창에서 첫 반복의 TPOT는 휴리스틱보다 16% 길다, 배율 0.86). 이 값은 간섭이 아니라 정책 비용이다(nvidia-smi 기록에 다른 프로세스가 없고 attention·step 시간은 반복 0과 1·2에서 같다). 보고서에는 정책 캐시 규약(첫 반복 포함 여부)을 반드시 병기해야 한다.

- **분기(휴리스틱 대비).** table은 300개 요청 중 10개에서 토큰이 갈렸다(table 분기 지점 10곳; hybrid 10곳, model 8곳; 불일치 토큰 table 921개, hybrid 921개, model 740개 — 갈린 뒤의 누적 포함, 정책마다 토큰이 반복 3회 같은 자리에서 갈림). 교사 강제 진단은 처음 400 decode 호출에서 정책마다 8,684행을 기록했고 그중 argmax가 바뀐 행은 1개(table; 요청 16 위치 30, bf16 1 ulp 동점)다. 분류된 것은 1곳(동점 1 ulp)이고 나머지 9곳(model은 7곳)은 교사 강제 구간 밖이라 **미분류**다. 분류된 구간에서 clear는 없다; 미분류 지점이 clear인지는 알 수 없다(GPU 재실행이 필요하다). 교사 강제 구간은 평균 배치가 낮은 도입부라 §3의 기존 분류와 직접 비교하지 않는다.

- **FA2 혼합 길이 step은 81.0 ms로 균일(FA2 균일 14.6 ms)의 5.5배, CUDA graph 혼합 80.6 ms 대 CUDA graph 균일 13.7 ms로 5.9배다.** 이 증상은 10월 6일 재현(5.46배)과 같은 크기이고, 이번 프로파일은 그 원인을 분리한다: 차이를 만드는 것은 attention GPU 시간이다 — FA2 eager에서 혼합 step의 attention이 67.7 ms(attention 67.7 ms, GPU busy의 87%)이고 균일은 2.95 ms다. 혼합−균일 step 시간 차이의 97.6%가 attention GPU 시간 차이다(차이의 97.6%; FlashInfer는 차이의 97.4%). - **자연 대조 실험: 32K 요청이 끝난 직후.** 혼합 실행의 마지막 decode iteration(요청이 31개로 줄고 32K 요청이 빠진 뒤)의 attention이 2.89 ms로 떨어진다(67.7 → 2.9 ms, 같은 엔진·같은 프로세스).

**vLLM 0.31의 혼합 길이 손실은 무엇이 지배하는가.** 이 설정에서는 attention 커널의 GPU 시간이다(혼합−균일 차이의 98%, FA2·FlashInfer 모두). 호스트 오버헤드·GEMM·CUDA graph 여부는 지배 요인이 아니다. 분할 수 휴리스틱이 직접 원인이라는 증거(커널 이름의 분할 수, 분할 8로 바꾼 재실행)는 이 프로파일에 없다: 같은 배치의 격자 측정(휴리스틱 1.07 ms/층, 분할 8 0.28 ms/층)과 엔진 측정이 일치한다는 정황 증거만 있다.

**본 작품의 기전이 운영 엔진에서 성립하는 조건(이 측정이 보인 범위).**
1. 증상은 vLLM 0.31(기본 FA2 백엔드, RTX 4090, 긴 요청 1개 + 짧은 요청 31개)에서 재현되고 attention이 step의 87%를 차지한다 — 해결할 시간이 있다. 이 시간 중 커널 격자의 분할 비(3.8배)가 그대로 옮겨진다면 step은 81 ms에서 약 31 ms로 줄 수 있다는 계산이 나오지만 이것은 측정이 아니라 격자 배율을 그대로 적용한 가정이다.
2. 그러나 vLLM의 FA2 래퍼는 `num_splits`를 0(C++ 휴리스틱)과 1만 받으므로(소스 인용 위 §8) 외부에서 분할 수를 고르는 방식은 C++ 래퍼 수정 없이는 적용되지 않는다. FlashInfer 백엔드는 tensor core 변형으로 고정되어 있어(`flashinfer.py:1259-1264`) 혼합 길이에서 24.0 ms attention이 남고, CUDA-core 변형을 고르는 설정은 노출되어 있지 않다.
