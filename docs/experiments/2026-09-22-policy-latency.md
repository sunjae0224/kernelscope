# 모델 선택의 CPU 비용 개선

기존 모델 정책은 새로운 KV 페이지 구성을 만나면 9개 후보를 예측했다. 이벤트 시뮬레이터가 작은 NumPy 배열을 수만 번 만들고 줄이는 작업이 병목이었다. 페이지 구성 캐시는 이후 호출에 도움이 됐지만, 최초 호출과 새 요청 합류 시의 계산 비용은 남아 있었다.

같은 이벤트 순서, CTA 입장 순서, 임계값과 부동소수점 합산 순서를 유지하는 C 실행 경로를 추가했다. 피팅 계수·후보 집합·페이지 캐시 기준은 바꾸지 않았다. `-fno-fast-math -ffp-contract=off`로 컴파일하고 NumPy 구현을 독립 기준으로 보존한다. 컴파일러가 없는 환경에서는 기준 구현을 사용한다.

## CPU 실측

기존 세 시나리오의 7개 페이지 구성마다 **새 정책 객체를 만들고 5회** 측정했다. 기준/개선 실행 순서를 교대로 바꿨다. 아래는 첫 선택의 중앙값이다. GPU 서빙 배율과는 다른 지표다.

| 구성 | NumPy 기준 | C 실행 | 감소 배율 |
|---|---:|---:|---:|
| Uniform 첫 선택 | 1,068.881 ms | 18.926 ms | 56.5× |
| Ragged 첫 선택 | 842.600 ms | 14.293 ms | 59.0× |
| Arrivals 혼합 배치 | 348–963 ms | 6.468–17.213 ms | 53.8–59.1× |
| 마지막 단일 요청 | 4.824 ms | 0.519 ms | 9.3× |

캐시 hit 비용은 C 경로에서 0.902–5.567µs였다. 최초 컴파일·로드에는 별도로 **55.683ms**, 이미 만들어진 라이브러리의 로드·초기화에는 **1.537ms**가 들었다. 이 비용은 첫 선택 측정에서 제외했으며, 서빙 결과에도 `policy_setup_runs`로 별도 기록한다. 미래 입력의 선택 결과를 미리 계산하지 않는다.

## 동작 검증

- 무작위 220개 실행, 임계값·대형 grid·입력 오류·컴파일 실패 대체 경로를 검증했다.
- 위 7개 구성에서는 모든 후보의 예측 시간 차이가 **0**, 순위와 선택 split도 동일했다.
- 동일한 결과는 이 환경과 검증 입력에서 확인했다. 다른 NumPy·컴파일러·CPU에 대해 모든 입력의 비트 동일성을 보장한다는 뜻은 아니다.
- 타이밍 예측 오차나 최악 선택 손실을 새로 개선한 것은 아니다. 동일한 예측을 계산하는 CPU 비용을 줄였다.

원본 반복값·프로파일·컴파일 옵션·소스 해시: [policy-latency.json](policy-latency.json).

```bash
.venv/bin/python -m scripts.benchmark_policy_latency \
  --repeats 5 --out docs/experiments/policy-latency-new.json
KERNELSCOPE_SIMULATOR=python .venv/bin/python -m kernelscope.cli serve run ...
```

출력 파일이 이미 있으면 덮어쓰지 않는다. 실제 생성 지연에 대한 영향은 [후속 서빙 검증](followup/README.md)에서 별도로 확인한다.
