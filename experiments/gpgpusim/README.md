# GPGPU-Sim 실험 (GPU 없는 노트북)

목적: 실제 GPU 없이 사이클 수준 시뮬레이터로 **KV 분할 수에 따른 부하 불균형 기전**을 정성적으로 재현한다. RTX 4090 실측(kernelscope)의 절대 시간을 맞추는 보정이 아니라, "혼합 길이 배치에서는 분할 수가 커널 시간을 크게 바꾸고, 균일 배치에서는 그렇지 않다"는 경향을 다른 방법으로 한 번 더 확인하는 것이다.

## 환경 (2026-09-26 확인)

- GPGPU-Sim 4.2.0 dev(`a4ce3fe`), gcc-11, CUDA 11.8 툴킷(런타임 드라이버 없음). 빌드: 상위 작업 폴더(`/root/sunjae/gpu_graduation`)의 `./build_gpgpusim.sh` (`-j1`, 약 6분); 시뮬레이터 트리도 그 폴더에 있다.
- 실행 규칙(`run_sim.sh`): `nvcc -O3 -gencode arch=compute_70,code=compute_70 -Xfatbin=-compress=false --cudart shared`, 환경 변수 `CUOBJDUMP_SIM_FILE=1`, 구성 `SM7_QV100`(SM 80개, Volta). CUDA 11.8의 `cuobjdump` 출력 형식이 시뮬레이터의 옛 파서(CUDA 6 이전 규격)와 맞지 않아 그대로 실행하면 "No PTX sections found"로 중단되는데, `CUOBJDUMP_SIM_FILE=1`이 그 섹션 정리 단계를 건너뛰게 하고 PTX는 `cuobjdump -xptx`로 뽑은 파일에서 직접 읽힌다. 시뮬레이터 소스는 수정하지 않았다.
- 피해야 할 것 두 가지: `-lineinfo`는 인라인 함수에 `.loc … inlined_at` 지시문을 만들어 PTX 파서가 "Syntax error"로 멈춘다. `__shfl_xor_sync`로 워프 합산을 하면 기능 시뮬레이션 결과가 참조와 최대 8.6e-3 어긋났다(같은 커널을 공유 메모리 합산으로 바꾸면 2.2e-8). 시뮬레이터의 `shfl.sync` 모델 문제인지 확정하지 않았으므로 셔플을 쓰지 않는다.
- 동작 확인: `vecadd.cu` (65,536 원소) → 6,109 사이클, 1,376,256 명령어, 결과 일치. 로그 `results/gpgpusim-vecadd-SM7_QV100.log`.

## 커널

`splitkv_attn.cu`: fp32, d = 64, GQA, 디코드 attention의 split-KV 구조를 축소 구현한 것이다. 그리드 (S, B, H_q); 분할 s는 **캐시 용량(최대 길이)** 기준으로 자른 키 구간을 맡으므로, 짧은 요청의 뒤쪽 분할은 일을 하지 않는다(flash-attn과 같은 규칙). 블록 안에서는 스레드 128개가 온라인 softmax로 부분 결과를 만들고 트리 병합한다. S > 1이면 두 번째 커널이 (최댓값, 합, 누적) 삼중항을 합친다. CPU 배정밀도 참조와 비교해 최대 절대 오차 < 1e-3이면 `ok`.

```bash
FUNC=1 ./run_sim.sh splitkv_attn.cu /tmp/s4 8 8 2 4 "1024,128x7"   # 기능 검증만
./run_sim.sh splitkv_attn.cu results/gpgpusim/ragged_s4 8 8 2 4 "4096,128x7"   # 성능 시뮬레이션
```

## 스윕

`results/gpgpusim/splitkv_sweep.csv`: 혼합 길이(2048 × 1 + 128 × 15, 길이비 16)와 키 총량이 비슷한 균일 길이(256 × 16), B = 16, H_q = 8, H_kv = 2, S ∈ {1, 2, 4, 8, 16}. B × H_q = 128 = 0.8 × 2 × 80이므로 flash-attn 휴리스틱이라면 두 경우 모두 "이미 가득 찼다"고 보고 S = 1을 고르는 조건이다. 성능 시뮬레이션은 한 조건에 수 분이 걸린다(약 1,200만 명령어). 결과 해석은 아래에 추가한다.

## 결과 (2026-09-26, SM7_QV100)

| 배치 | S=1 | S=2 | S=4 | S=8 | S=16 | S=1 대비 최대 개선 |
|---|---:|---:|---:|---:|---:|---:|
| 혼합 길이 2048 + 128×15 (사이클) | 452,140 | 230,648 | 121,071 | 86,491 | 62,566 | **7.23배 (S=16, 계속 감소 중)** |
| 균일 길이 256×16 (사이클) | 53,004 | 31,388 | 24,515 | 23,506 | 26,102 | 2.25배 (S=8, S=16부터 악화) |
| 혼합 길이 IPC | 104.8 | 211.2 | 424.8 | 657.2 | 1,081.7 | |
| 균일 길이 IPC | 921.4 | 1,611.9 | 2,206.8 | 2,599.8 | 2,878.7 | |

두 배치의 키 총량은 거의 같다(3,968 vs 4,096). 그런데 S = 1에서 혼합 길이 배치는 균일 배치보다 **8.5배 오래** 걸리고 IPC는 1/9이다. 긴 요청 하나를 맡은 CTA 8개(헤드마다 하나)가 2,048개 키를 워프 4개로 순차 처리하는 동안 나머지 SM이 논다는, 실측에서 추정했던 부하 불균형이 사이클 수준에서 그대로 나타난다. 분할 수를 늘리면 혼합 길이 배치는 S = 16까지 계속 빨라져 7.23배가 되고(명령어 수는 43% 늘어남에도), 균일 배치는 S = 8에서 2.25배로 포화한 뒤 결합 비용 때문에 다시 느려진다. 실측(그림 4, RTX 4090: 혼합 길이 최악 12.53배 vs 균일 길이 손실 0.7%)과 같은 방향이다.

한계: 이 축소 커널은 CTA당 워프 4개뿐이라 S = 1에서 균일 배치도 SM을 다 채우지 못해 분할로 2.25배를 얻는다. 실제 FlashAttention-2 커널은 CTA 하나가 더 많은 병렬성을 갖고 텐서 코어를 쓰므로 균일 배치의 이득이 거의 없다. 따라서 이 결과는 "혼합 길이에서 분할 수가 훨씬 중요하다"는 **정성적 재현**이며, 절대 사이클이나 최적 분할 수를 실측과 맞춘 것은 아니다. 수치는 `kernelscope verify`의 `sim.*` 항목으로 재계산된다(`kernelscope/docs/experiments/gpgpusim-splitkv-sweep.csv`).
